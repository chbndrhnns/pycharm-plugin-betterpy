Stable build class / resource filtering (include-mode)¶

What this is¶

When the active release channel provides an explicit include: list (e.g. feature-sets/stable.yaml), the build filters the produced jar AND the test tasks (compileTestKotlin, test) to ship / compile / run ONLY:

  1. Infra code under FeatureFiltering.INFRA_INCLUDES (core/**, bootstrap/**, featureflags/**).
  2. Canonical feature packages for every id in the channel manifest: com/github/chbndrhnns/betterpy/features/<id_sanitized>/**, where <id_sanitized> is the lowerCamelCase conversion of the YAML id (hyphens removed, each subsequent piece title-cased), e.g. make-parameter-optional -> makeParameterOptional. An explicit package: override in the feature's metadata block wins over this default.
  3. Per-feature XML registrations under META-INF/features/:
  4. _*.xml — always-included meta-features such as _bootstrap.xml,
  5. <id>.xml — the canonical registration for each listed id,
  6. <id>.*.xml — sibling registrations (.pythonid.xml, .mcp.xml, .yamlsupport.xml, .structuralsearch.xml, .actions.xml, ...).
  7. Non-feature resources (plugin.xml, generated aggregators, icons, messages, inspection/intention descriptions, feature-sets manifests).

Everything else under features/** — compiled classes AND META-INF/features XMLs that do not belong to a listed id — is dropped from the jar and from test compilation/execution.

For a wildcard manifest (include: "*") or a missing manifest (the dev channel case), no filter is applied: the full jar and full test suite behave exactly as they did before this mechanism existed.

Why include-mode¶

The previous implementation subtracted excluded ids from a known-canonical set, which meant anything that did not sit under the canonical features/<id_sanitized>/ layout (camelCase of the id) was silently kept. Category packages such as features/intentions/** or features/inspections/** escaped the filter entirely because their ids never matched a canonical package.

Include-mode flips the contract: "ship only what is listed" — deterministic regardless of how many category-package features exist. The downside is documented below under "Migration implications".

Where it lives¶

All the logic is in build.gradle.kts:

  • object FeatureFiltering — shared data used by every consumer:
  • resolveIncludedFeatureIds(channel, yamls) — returns the channel's include set, or null for wildcard / missing manifest.
  • INFRA_INCLUDES — the infra allow-list. Add future infra roots here and every consumer (jar, compileTestKotlin, test) picks them up.
  • featureIncludePatterns(ids) — canonical features/<id_sanitized>/** globs for the listed ids.
  • resourceIncludePatterns(ids) — META-INF/features/_*.xml, <id>.xml, and <id>.*.xml globs.
  • tasks.jar — resolves the include set in doFirst, then adds INFRA_INCLUDES, per-feature class globs, and the non-feature resource roots as include(...) patterns. Also emits a logger.warn listing any channel ids that have no canonical package on disk.
  • processResources — applies the same decision to META-INF/features/*.xml entries (scoped eachFile-exclude that keeps _-prefixed ids plus listed <id>s).
  • testFeatureIncludePatterns — captured at configuration time and wired into compileTestKotlin { include(...) } and test { include(...) } when the manifest is explicit.

_bootstrap and any other _-prefixed id remain unconditionally included.

Migration implications for un-migrated features¶

Under include-mode, a feature id in stable.yaml only ships if its canonical package features/<id_sanitized>/ exists on disk. Category-package features (those whose source still lives under features/intentions/<x>/, features/inspections/<x>/, etc.) are intentionally dropped from the stable jar until they are migrated.

The build emits a diagnostic logger.warn during jar listing every such orphan id so reviewers notice. Example:

Stable-build filtering (channel='stable'): 3 included id(s) have no canonical
features/<id_sanitized>/ package and will NOT ship in this jar:
some-category-feature, ... Migrate them into canonical packages or remove
from the channel manifest.

Migrating a category-package feature into include-mode¶

  1. Create src/main/kotlin/com/github/chbndrhnns/betterpy/features/<id_sanitized>/ (camelCase conversion of the id, e.g. make-parameter-optional -> makeParameterOptional).
  2. Move the feature's classes under that package; keep all shared / cross- cutting code in core/ / featureflags/.
  3. Update imports, run ./gradlew test, and verify the StableJarPackageFilteringTest integration test still passes with -Dbetterpy.enableSlowIntegrationTests=true.
  4. The next ./gradlew jar -PreleaseChannel=stable will include the migrated feature; the logger.warn for that id disappears.

Category directories (features/intentions/**, features/inspections/**, ...) can remain as long as the features they hold are listed in dev.yaml only. They will not ship in stable, by design.

Testing¶

  • Unit sanity (FeatureFilteringHelpersTest, always run): pins the infra allow-list, feature-id sanitization, and resource-glob shapes against fixture inputs.
  • End-to-end (StableJarPackageFilteringTest, opt-in via -Dbetterpy.enableSlowIntegrationTests=true): builds :jar with -PreleaseChannel=stable and -PreleaseChannel=poc-excluded, then asserts:
  • the pilot feature (strip-signature-type-annotations) and its XML are present under stable and absent under poc-excluded;
  • a non-listed canonical feature's class is ABSENT under stable (regression guard for include-mode);
  • an infra class under core/** is present under BOTH channels;
  • META-INF/plugin.xml and the generated META-INF/plugin-features-index.xml aggregator are present under BOTH channels (regression guard against over-filtering resources);
  • _bootstrap.xml is present under BOTH channels.

Gotchas¶

  • _bootstrap and any _-prefixed id must always be included — same rule as in GeneratePluginXmlFragmentsTask; the helpers in FeatureFiltering enforce it.
  • PluginSettingsState still carries toggles for features that may not ship in the current channel — that is fine, because the runtime only reads them when the corresponding extension is registered (the XML filter handles that in lock-step with the class filter).
  • Repository guideline applies: if you change PluginSettingsState or the feature filter itself, run one clean build without caches: ./gradlew clean build --no-build-cache.
  • @RequiresFeature("...") gates continue to work — under include-mode the corresponding test classes are simply not compiled in channels that don't list the feature, which is the desired outcome.

Historical context (exclude-mode)¶

The mechanism started as an exclude-mode filter in an earlier iteration of this file. That approach was superseded because un-migrated category-package features silently escaped the subtraction. Include-mode, documented above, is the current authoritative behavior. Two alternative approaches were considered and rejected for this iteration:

  • Per-feature Gradle subprojects / source sets — cleanest long-term design but too invasive for this iteration.
  • ProGuard / R8 tree-shaking — painful reflection / service-loader configuration for an IntelliJ Platform plugin; easy to break at runtime.
