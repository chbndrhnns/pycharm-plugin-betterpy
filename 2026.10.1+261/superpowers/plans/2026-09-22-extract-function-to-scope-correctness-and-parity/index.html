Extract Function to Scope Correctness and Parity Implementation Plan¶

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Make Extract Function to Scope preserve Python behavior for supported selections, reject unsafe transformations without edits, and add module-level source selection plus a safe class destination comparable to IntelliJ's Kotlin counterpart.

Architecture: Separate selection, flow analysis, destination planning, and mutation. After the user chooses a destination and name, build a destination-specific plan from PyCharm's public control-flow and scope APIs; validate both the helper's references and the replacement call before entering one write command. The processor applies only a validated plan and reports whether it actually changed the file.

Tech Stack: Kotlin/JVM 25, IntelliJ Platform/PyCharm 2026.2 PSI and control-flow APIs, JUnit 4 light fixture tests.

Spec: The current feature contract in docs/features/extract-function-to-scope.md, plus the eight review findings in the task that requested this plan. This plan resolves the current contract's explicit class-body and top-level exclusions as the final parity phase.

Global Constraints¶

  • Do not read or change spec/.
  • Use only public IntelliJ and bundled Python APIs; run Plugin Verifier before shipping any newly used API.
  • Run UI-triggered PSI, index, type, and scope analysis in ReadAction.nonBlocking(...).inSmartMode(project); finish on the UI thread only to present choices and apply a still-current result. Keep dialogs and write commands off the read path.
  • Preserve one undoable edit and record recent usage and analytics only after a successful, non-preview application.
  • A rejected or stale plan must leave the source text unchanged.
  • Keep extract-function-to-scope in the dev feature set; do not promote since: 'NEXT' or add it to stable as part of these fixes.
  • Use conventional commits; each task below must leave its focused tests passing.

Review Focus¶

The owning task must add a test for each of these inputs, even if its main reproduction differs:

  1. A name read inside a lambda or nested def before its outer assignment must not become an eager call argument; reject when moving the closure would change its binding (Task 2).
  2. A parameter or imported name shadowing the new helper at the call site must be rejected (Task 4).
  3. A selection in a decorator, default argument, or annotation must be rejected without mutation until header extraction is supported (Task 1).
  4. A method inside nested classes must place a requested module helper in the PyFile, not a class body (Task 5).
  5. A local or enclosing helper must not displace the first docstring statement (Task 5).

Sequence and acceptance¶

Tasks 1–5 are correctness gates. They may keep the existing destination set, but must make every advertised destination safe. Tasks 6–7 add source/destination parity with Kotlin. Do not widen action availability before Task 6 has tests for top-level selection, or offer a class destination before Task 7 has receiver and binding tests. Each task uses red/green tests and ends with its own atomic commit.
