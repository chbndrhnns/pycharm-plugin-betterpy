Documentation Development¶

This project uses Zensical with the Material for MkDocs theme to manage its documentation.

Local Setup¶

To serve and preview the documentation locally, you'll need uv installed.

  1. Serve the documentation (with live-rendered placeholders): 

    scripts/build_docs.py serve

    This wraps zensical serve and starts a local preview at http://127.0.0.1:8000/. The page reloads when you edit anything under docs/ or any feature metadata block under src/main/resources/META-INF/features/*.xml.

    Do not run uv run zensical serve directly

    Our docs use placeholders such as 64, 5, and <!-- feature: <id> --> blocks that are expanded from feature metadata at render time. A plain zensical serve does not invoke that rendering pipeline, so the live preview will show the raw placeholders rather than the production output. Always use the scripts/build_docs.py wrapper.

  2. Build the site once: 

    scripts/build_docs.py build
    Produces site/, matching what the release pipeline builds.

  3. Add a new dependency: 

    uv add <package-name>

How the docs build works¶

The committed files under docs/ are the single source of truth and are never mutated by any build or serve command. Both scripts/build_docs.py build and scripts/build_docs.py serve first render every docs/**/*.md file into a shadow directory at build/docs-rendered-root/docs/ (git-ignored), expanding placeholders and feature blocks, then run zensical against that shadow tree. The committed zensical.toml is likewise copied (nav-trimmed for empty groups) rather than rewritten in place. See scripts/build_docs.py and scripts/docs_ext.py in the repo for details.

Recovery¶

If git status shows unexpected changes under docs/ — typically left over from an interrupted run of the legacy pre-refactor script — restore them with:

git checkout -- docs/

The current pipeline never writes into docs/, so such leftovers can only come from an older version of the build script or from manual edits.

Project Structure¶

  • zensical.toml: Configuration file for the documentation (theme, navigation, extensions).
  • docs/: Directory containing the Markdown source files for the documentation.
  • docs/index.md: The home page of the documentation.

Updating Marketplace Screenshots (UI Tests)¶

The documentation and marketplace page rely on automated screenshots generated by UI tests. Since these tests require a running IDE instance via the Robot Server plugin, they are excluded from the standard ./gradlew test task.

To regenerate these screenshots locally:

  1. Start the IDE with the Robot Server: 

    ./gradlew runIdeForUiTests
    Wait for the PyCharm IDE to fully start.

  2. Run the screenshot test class in a separate terminal: 

    ./gradlew test --tests "*PluginPageScreenshotsTest*"

The new screenshots will be saved automatically to docs/assets/marketplace/ and can be committed.

Updating Feature GIFs (Starter/Driver)¶

New feature recordings should use JetBrains Starter + Driver. The Driver test generates component-scoped PNG frames under build/docs-recordings/<scenario>/, then a small script encodes those frames into a GIF for the docs.

For the Hide overloads Structure View recording:

JAVA_HOME=/Users/jo/Library/Java/JavaVirtualMachines/jbr-21.0.10/Contents/Home ./gradlew integrationTest --tests "*HideOverloadsDocsRecordingTest"
scripts/build-docs-gif.sh hide-overloads

The committed output is docs/assets/features/structure-view-overload-hiding/hide-overloads.gif.

Updating Stable Feature Media¶

Stable feature docs media is tracked in scripts/stable-feature-media.tsv. Each feature in src/main/resources/feature-sets/stable.yaml must appear in that manifest as either:

  • auto: recorded by recording-lab through IDE remote control and encoded as optimized MP4 by scripts/build-docs-mp4-from-video.sh
  • nonvisual: no meaningful user-facing IDE surface for docs media

To regenerate all automated stable feature MP4s:

JAVA_HOME=/Users/jo/Library/Java/JavaVirtualMachines/jbr-21.0.10/Contents/Home scripts/build-stable-feature-media.sh

If cropped recordings already exist under build/stable-feature-recordings/stable-feature-docs-features__<feature-id>/, skip the expensive IDE recording step and only re-encode:

scripts/build-stable-feature-media.sh --skip-recordings

The MP4 processing step reads raw.mp4 plus the recording-lab geometry-overlay.json/timeline.jsonl artifacts, derives an ffmpeg crop, and then applies crop, frame-rate reduction, scaling, H.264 encoding, and faststart optimization. Use CROP_MARGIN=<pixels> to tune the default crop padding without re-recording.

For one feature:

scripts/build-stable-feature-media.sh --skip-recordings --feature inherited-attribute-documentation

The manifest is guarded by:

uv run pytest scripts/test_stable_feature_media.py -q

Pytest Fixture Engine Performance (home-assistant/core)¶

Measure fixture-consumer latency only through a deployed development plugin in an installed PyCharm 261. Do not substitute a Gradle integrationTest, Starter/Driver live test, or a Gradle-launched IDE: those paths do not exercise the deployed IDE process used for this benchmark.

The benchmark corpus is deliberately a shallow sparse checkout containing only tests/. It supplies the fixture declarations and their consumers, but is not a complete or pytest-executable Home Assistant checkout. Reuse a prepared checkout when it contains tests/conftest.py; otherwise create the pinned corpus once:

export BENCHMARK_REF=2026.7.1
export BENCHMARK_REPO="$PWD/build/perf-repos/homeassistant-core-$BENCHMARK_REF"

git clone --depth 1 --filter=blob:none --branch "$BENCHMARK_REF" --sparse \
  https://github.com/home-assistant/core.git "$BENCHMARK_REPO"
git -C "$BENCHMARK_REPO" sparse-checkout set --cone tests
test -f "$BENCHMARK_REPO/tests/conftest.py"

Deployed PyCharm 261 benchmark¶

Choose one installed build whose displayed Build value begins 261.. The deployment command enables the diagnostic channel only for this benchmark. It also records the exact selected build in build/perf-reports/deploy.log; that value, rather than a guessed 261.* value, is passed to the report.

export BENCHMARK_TOKEN=ha-fixture-perf-secret
export BENCHMARK_REQUESTED_PORT=63342
export DEPLOY_LOG="$PWD/build/perf-reports/deploy.log"
mkdir -p "$(dirname "$DEPLOY_LOG")"

set -o pipefail
BETTERPY_REQUIRED_PYCHARM_BUILD=261 \
BETTERPY_REMOTE_CONTROL_ENABLED=true \
BETTERPY_REMOTE_TOKEN="$BENCHMARK_TOKEN" \
BETTERPY_IDE_SERVER_PORT="$BENCHMARK_REQUESTED_PORT" \
./scripts/deploy.sh "$BENCHMARK_REPO" | tee "$DEPLOY_LOG"

export IDE_BUILD="$(awk '/^   Build   : 261\./ { print $3; exit }' "$DEPLOY_LOG")"
test -n "$IDE_BUILD"
printf 'Benchmarking deployed PyCharm build: %s\n' "$IDE_BUILD"

After indexing completes, ask the remote-control doctor for the endpoint. The requested server port is only a preference: use the baseUrl that doctor actually returns. The command below writes that result, extracts its discovered base URL, and does not reuse a hard-coded port in the benchmark request.

export DOCTOR_REPORT="$PWD/build/perf-reports/remote-doctor.json"

if ! BETTERPY_REMOTE_TOKEN="$BENCHMARK_TOKEN" \
  python3 scripts/ide_remote_control.py \
    --base "http://127.0.0.1:${BENCHMARK_REQUESTED_PORT}/api/betterpy-remote" \
    doctor --try-ports "63340,63341,63342,63343,63344,63345" \
    | tee "$DOCTOR_REPORT"; then
  echo "❌ IDE deployment is not ready." >&2
  exit 1
fi

if ! BENCHMARK_BASE_URL="$(python3 -c '
import json, sys
report = json.load(open(sys.argv[1], encoding="utf-8"))
if report.get("ready") is not True or not report.get("baseUrl"):
    raise SystemExit("doctor report is not ready")
print(report["baseUrl"])
' "$DOCTOR_REPORT")"; then
  echo "❌ IDE deployment is not ready." >&2
  exit 1
fi
export BENCHMARK_BASE_URL
printf 'Benchmarking doctor-discovered endpoint: %s\n' "$BENCHMARK_BASE_URL"

Run the driver for exactly one fixture in this IDE lifecycle. It verifies /ping, waits for smart mode, measures one process-cold request, performs one unreported warm-up, then records five warm requests. It fails on an empty usage response or a request above the 180-second hang ceiling, and writes JSON with the exact ideBuild, corpus ref, latency samples, and usage count.

python3 scripts/benchmark_homeassistant_fixture.py \
  --repo "$BENCHMARK_REPO" \
  --base-url "$BENCHMARK_BASE_URL" \
  --token "$BENCHMARK_TOKEN" \
  --fixture hass \
  --ide-build "$IDE_BUILD" \
  --ref "$BENCHMARK_REF" \
  --report "$PWD/build/perf-reports/hass.json"

enable_custom_integrations depends on hass; a hass request can warm the same analyzer path. To obtain an independent process-cold report for enable_custom_integrations, deploy/restart the same recorded PyCharm build, repeat the doctor step to set a new BENCHMARK_BASE_URL, then run:

python3 scripts/benchmark_homeassistant_fixture.py \
  --repo "$BENCHMARK_REPO" \
  --base-url "$BENCHMARK_BASE_URL" \
  --token "$BENCHMARK_TOKEN" \
  --fixture enable_custom_integrations \
  --ide-build "$IDE_BUILD" \
  --ref "$BENCHMARK_REF" \
  --report "$PWD/build/perf-reports/enable-custom-integrations.json"

Do not label a second fixture's first request in an already-used IDE process as process-cold. The driver reports end-to-end HTTP latency and usage counts; it does not attribute internal fixture-engine phases.

Post-benchmark cleanup¶

Disable the temporary diagnostic channel immediately after the final benchmark. Choose the same exact build recorded in IDE_BUILD from the filtered PyCharm menu. This deployment restarts that IDE with remote control disabled and clears the persisted remote-control token; no token or port is supplied to cleanup.

BETTERPY_REQUIRED_PYCHARM_BUILD=261 \
BETTERPY_REMOTE_CONTROL_ENABLED=false \
./scripts/deploy.sh "$BENCHMARK_REPO"

Import-alias Find Usages Performance (home-assistant/core)¶

Measure import-alias Find Usages through a deployed development plugin in an installed PyCharm 261 and a complete Home Assistant checkout. The sparse tests/ corpus used by the fixture-engine benchmark does not contain the production aliases required by this benchmark.

The pinned workload is Home Assistant 2026.7.1:

export BENCHMARK_REF=2026.7.1
export BENCHMARK_REPO="$PWD/build/perf-repos/homeassistant-core-$BENCHMARK_REF"

git clone --depth 1 --branch "$BENCHMARK_REF" \
  https://github.com/home-assistant/core.git "$BENCHMARK_REPO"
test -f "$BENCHMARK_REPO/homeassistant/core.py"

Deploy the plugin with remote control enabled and discover the actual endpoint using the same Deployed PyCharm 261 benchmark and doctor procedure above. Keep the selected IDE_BUILD, doctor-discovered BENCHMARK_BASE_URL, and token for the following command:

python3 scripts/benchmark_import_alias_find_usages.py \
  --repo "$BENCHMARK_REPO" \
  --base-url "$BENCHMARK_BASE_URL" \
  --token "$BENCHMARK_TOKEN" \
  --ide-build "$IDE_BUILD" \
  --ref "$BENCHMARK_REF" \
  --label "candidate" \
  --report "$PWD/build/perf-reports/import-alias-candidate.json"

The driver waits for smart mode, then runs the default alternating order:

disabled → enabled → enabled → disabled

Every block changes the import-alias-find-usages feature flag, discards one priming request, and records seven paced warm requests. It fails rather than producing a misleading report when a result set changes within or between blocks.

For the pinned corpus and target positions, the default result contract is:

Workload Disabled Enabled Required invariant
DOMAIN at homeassistant/core.py:121:1 138 usages 450 usages Disabled locations are a subset of enabled locations; the 312 enabled-only locations contain HOMEASSISTANT_DOMAIN.
BLOCK_LOG_TIMEOUT at homeassistant/core.py:124:1 4 usages 4 usages Location sets are identical.

The DOMAIN workload measures the complete user-visible cost of returning alias-derived locations. The control separates that cost from the always-on feature-gate and no-alias discovery cost. Counts are deliberately overridable for a different pinned corpus with:

--disabled-alias-usage-count
--enabled-alias-usage-count
--enabled-only-alias-usage-count
--control-usage-count

Do not compare means when an IDE pause produces an outlier. The JSON report retains every sample and reports median, mean, minimum, and maximum for each workload/mode. Compare warm medians and first confirm every result-set invariant.

Candidate-versus-baseline A/B¶

The driver compares the feature enabled and disabled within one deployed build. To compare two plugin implementations, run it for both commits and repeat in the opposite deployment order:

baseline deploy → baseline report
candidate deploy → candidate report
candidate deploy → candidate repeat report
baseline deploy → baseline repeat report

Use the same Home Assistant checkout, installed PyCharm build, JBR, target positions, sample count, and request pacing for every run. Record the commit in --label, for example --label "$(git rev-parse --short HEAD)". Do not claim a cross-build speedup unless both implementations preserve the same enabled location set and the repeated medians agree directionally.

Optional CPU sampling¶

Wall-clock reports answer whether the user waits longer. Capture JFR for the enabled alias block when CPU attribution is needed:

export IDE_PID="$(pgrep -f '/Applications/PyCharm.*\.app/Contents/MacOS/pycharm')"
jcmd "$IDE_PID" JFR.start \
  name=import-alias \
  settings=profile \
  filename="$PWD/build/perf-profiles/import-alias.jfr"

# Run benchmark_import_alias_find_usages.py here.

jcmd "$IDE_PID" JFR.stop name=import-alias
jfr print --events jdk.ExecutionSample \
  "$PWD/build/perf-profiles/import-alias.jfr"

Compare stacks containing PyAliasUsageCollector, KnownSymbols, PSI equivalence, Python resolution, word search, and result deduplication. A JFR profile attributes CPU work but does not replace the response-time and result-location checks in the JSON report.

After every run, apply the remote-control cleanup procedure above. The default driver order ends with the feature disabled, but the temporary remote endpoint and token still require deployment cleanup.

Web Framework Discovery Diagnostics (home-assistant/core)¶

Measure one direct, all-framework web-application discovery scan through a deployed development plugin in an installed PyCharm 261. This procedure requires the complete Home Assistant source tree: the sparse tests/ corpus above is suitable for the fixture-engine benchmark only and cannot establish web-framework discovery behavior.

Reuse a prepared checkout when it contains homeassistant/components; otherwise create the pinned full-source corpus:

export DISCOVERY_REF=2026.7.1
export DISCOVERY_REPO="$PWD/build/perf-repos/homeassistant-core-$DISCOVERY_REF-full"
git clone --depth 1 --branch "$DISCOVERY_REF" \
  https://github.com/home-assistant/core.git "$DISCOVERY_REPO"
test -d "$DISCOVERY_REPO/homeassistant/components"

Deployed PyCharm 261 diagnostic¶

Choose one installed build whose displayed Build value begins 261.. Deploy the full checkout with remote control enabled, retain the exact selected build from the deploy log, and use that same build for cleanup after collecting the report:

export DISCOVERY_TOKEN=ha-web-discovery-secret
export DISCOVERY_REQUESTED_PORT=63342
export DISCOVERY_DEPLOY_LOG="$PWD/build/perf-reports/web-discovery-deploy.log"
mkdir -p "$(dirname "$DISCOVERY_DEPLOY_LOG")"

set -o pipefail
BETTERPY_REQUIRED_PYCHARM_BUILD=261 \
BETTERPY_REMOTE_CONTROL_ENABLED=true \
BETTERPY_REMOTE_TOKEN="$DISCOVERY_TOKEN" \
BETTERPY_IDE_SERVER_PORT="$DISCOVERY_REQUESTED_PORT" \
./scripts/deploy.sh "$DISCOVERY_REPO" | tee "$DISCOVERY_DEPLOY_LOG"

export DISCOVERY_IDE_BUILD="$(awk '/^   Build   : 261\./ { print $3; exit }' "$DISCOVERY_DEPLOY_LOG")"
test -n "$DISCOVERY_IDE_BUILD"
printf 'Running web-discovery diagnostics in deployed PyCharm build: %s\n' "$DISCOVERY_IDE_BUILD"

After the full project opens and begins indexing, ask doctor for the live endpoint. The requested port is only a preference: once doctor returns its baseUrl, use DISCOVERY_BASE_URL, not the requested port, for every subsequent command.

export DISCOVERY_DOCTOR_REPORT="$PWD/build/perf-reports/homeassistant-web-discovery-doctor.json"

if ! BETTERPY_REMOTE_TOKEN="$DISCOVERY_TOKEN" \
  python3 scripts/ide_remote_control.py \
    --base "http://127.0.0.1:${DISCOVERY_REQUESTED_PORT}/api/betterpy-remote" \
    doctor --try-ports "63340,63341,63342,63343,63344,63345" \
    | tee "$DISCOVERY_DOCTOR_REPORT"; then
  echo "IDE deployment is not ready." >&2
  exit 1
fi

if ! DISCOVERY_BASE_URL="$(python3 -c '
import json, sys
report = json.load(open(sys.argv[1], encoding="utf-8"))
if report.get("ready") is not True or not report.get("baseUrl"):
    raise SystemExit("doctor report is not ready")
print(report["baseUrl"])
' "$DISCOVERY_DOCTOR_REPORT")"; then
  echo "IDE deployment is not ready." >&2
  exit 1
fi
export DISCOVERY_BASE_URL
printf 'Running against doctor-discovered endpoint: %s\n' "$DISCOVERY_BASE_URL"

Wait for smart mode and normal IDE readiness before the scan:

BETTERPY_REMOTE_TOKEN="$DISCOVERY_TOKEN" \
python3 scripts/ide_remote_control.py --base "$DISCOVERY_BASE_URL" \
  wait-ready --timeout-ms 240000 --poll-ms 250

Save the authoritative runtime schema and the diagnostic report:

BETTERPY_REMOTE_TOKEN="$DISCOVERY_TOKEN" \
python3 scripts/ide_remote_control.py --base "$DISCOVERY_BASE_URL" schema \
  > "$PWD/build/perf-reports/homeassistant-web-discovery-schema.json"

BETTERPY_REMOTE_TOKEN="$DISCOVERY_TOKEN" \
python3 scripts/ide_remote_control.py --base "$DISCOVERY_BASE_URL" \
  web-discovery-diagnostics \
  > "$PWD/build/perf-reports/homeassistant-web-discovery.json"

Rank counters.phaseTimings by totalNanos. Then compare fullPythonMarkerScanFilesExamined, routeObjectCandidateFiles, indexedCandidateFiles, and discoveryFiles to distinguish broad candidate scans from PSI/type-inference, route-graph, and OpenAPI work. This command measures direct scanner time, not cache-hit latency.

Post-benchmark cleanup¶

After saving the report, deploy with remote control disabled and select the same exact PyCharm build recorded in DISCOVERY_IDE_BUILD. This existing cleanup deployment clears the persisted remote-control token; do not supply a token or port.

BETTERPY_REQUIRED_PYCHARM_BUILD=261 \
BETTERPY_REMOTE_CONTROL_ENABLED=false \
./scripts/deploy.sh "$DISCOVERY_REPO"
