File-Based vs Stub-Based Indices in IntelliJ Platform¶

This document explains the two main indexing mechanisms available in the IntelliJ Platform, and why PyLambdaFileIndex correctly uses a file-based index rather than a stub-based one.

The Two Indexing Mechanisms¶

File-Based Indices (FileBasedIndexExtension)¶

A file-based index operates directly on raw file content. The platform feeds each file's bytes (and optionally its PSI tree) to a DataIndexer, which produces a map of keys → values. The index is stored on disk and queried via FileBasedIndex.getInstance().

Key characteristics:

  • Input: raw FileContent (bytes + lazily-built PSI). The indexer receives a FileContent object and can call inputData.psiFile to get the PSI tree.
  • Scope: any file type — source files, library JARs, .class files, .xml, etc.
  • Query API: FileBasedIndex.getContainingFiles(name, key, scope), getValues(...), getAllKeys(...).
  • Rebuild trigger: the file's content changes (timestamp/hash).
  • Base class: ScalarIndexExtension<K> (keys only, no values) or FileBasedIndexExtension<K, V>.

Stub-Based Indices (StubIndexExtension)¶

A stub index operates on the stub tree — a lightweight, serialisable skeleton of the PSI tree that captures only the declarations (classes, functions, fields, top-level assignments, etc.) without method bodies or expressions.

Key characteristics:

  • Input: a StubElement tree produced by the language's IStubFileElementType / StubElementType. The stub tree is built once and cached separately from the full PSI.
  • Scope: only files whose language has a stub-producing element type. For Python this means .py files processed by PyFileElementType.
  • Query API: StubIndex.getInstance().get(key, name, project, scope) — returns PSI elements directly (e.g. PyFunction, PyClass).
  • Rebuild trigger: the stub tree changes (i.e. the file's declarations change).
  • Base class: StringStubIndexExtension<Psi> or StubIndexExtension<K, Psi>.
  • Populated via: indexStub(stub, sink) on a StubElementType, or via a CustomTargetExpressionStubType extension point (see fixture-stub-index.md).

When to Use Each¶

Criterion File-Based Index Stub-Based Index
What you need to find Files (or arbitrary data) Named declarations (classes, functions, …)
Data lives in Expressions, bodies, any syntax Top-level / class-level declarations only
Language requirement Any file type Language must produce stubs
Query returns VirtualFile or raw values PSI elements
Typical use case "Which files contain X?" "Give me the PyFunction named foo"

Rule of thumb: use a stub index when you are indexing named declarations that appear in the stub tree. Use a file-based index when you need to record a fact about a file as a whole, or when the data you care about lives inside expressions or function bodies (which are not part of the stub tree).

Why PyLambdaFileIndex Must Be File-Based¶

PyLambdaFileIndex (in core/index/PyLambdaFileIndex.kt) answers the question:

"Which Python source files contain at least one lambda expression?"

There are two concrete reasons why a stub-based index cannot answer this question.

1. Lambda expressions are not part of the stub tree¶

The Python stub tree captures declarations: PyFunction, PyClass, PyTargetExpression at module/class scope, etc. A PyLambdaExpression is an expression — it can appear inside a function body, a default argument, a list comprehension, or any other expression context. Expression nodes are deliberately excluded from stubs to keep them small and fast.

Because PyLambdaExpression nodes are never present in the stub tree, a StubElementType for them cannot be registered, and indexStub() would never be called for them. A stub index simply has no access to this data.

2. The index records a file-level fact, not a named declaration¶

PyLambdaFileIndex stores a single marker key ("lambda") per file — it is a boolean "this file has lambdas" flag. Stub indices are designed to map names to PSI elements (e.g. function name → PyFunction). There is no named declaration to return here; the caller only needs the VirtualFile to open it and inspect it further.

The query call in the companion object reflects this exactly:

// PyLambdaFileIndex.kt
fun findFilesWithLambdas(project: Project, scope: GlobalSearchScope): Collection<VirtualFile> {
    return FileBasedIndex.getInstance().getContainingFiles(NAME, LAMBDA_MARKER, scope)
}

getContainingFiles is a FileBasedIndex API — there is no equivalent on StubIndex because stub queries return PSI elements, not files.

3. The indexer uses the full PSI tree¶

The indexer calls PsiTreeUtil.findChildOfType(psiFile, PyLambdaExpression::class.java), which walks the complete PSI tree including all expression nodes. This is only possible in a DataIndexer that receives a FileContent object with a lazily-built full PSI tree. A stub-based indexer only ever sees the stub tree, which, as noted above, contains no PyLambdaExpression nodes.

// PyLambdaFileIndex.kt — indexer body
override fun getIndexer(): DataIndexer<String, Void, FileContent> {
    return DataIndexer { inputData ->
        val result = mutableMapOf<String, Void?>()
        if (inputData.fileType == PythonFileType.INSTANCE) {
            val psiFile = inputData.psiFile as? PyFile ?: return@DataIndexer result
            // PsiTreeUtil walks the FULL PSI tree — not available in stub indexers
            val hasLambda = PsiTreeUtil.findChildOfType(psiFile, PyLambdaExpression::class.java) != null
            if (hasLambda) result[LAMBDA_MARKER] = null
        }
        result
    }
}

Contrast: When a Stub Index Would Be Correct¶

For comparison, consider fixture-stub-index.md, which describes indexing assigned fixtures of the form x = pytest.fixture()(func). That case is a good fit for a stub index because:

  • The indexed node is a PyTargetExpression — a top-level assignment, which is part of the stub tree.
  • The query returns a named PSI element (PyTargetExpression for fixture name x).
  • The CustomTargetExpressionStubType extension point already hooks into stub building for exactly this pattern.

PyLambdaFileIndex is the opposite: the data lives in expressions (not declarations), the result is a file (not a PSI element), and the detection requires a full-PSI walk. A file-based index is therefore not just acceptable — it is the only correct choice.
